# LaunchPad

> A simple starting point for building .NET applications on Specular and Dovetail.

One line to opt in Name the [LaunchPad SDK](concepts/launchpad-sdk/) next to your project’s SDK. It finds the host model and adds the LaunchPad and Dovetail packages that fit. Wiring as Joints Health checks, logging, telemetry, validation and time are [Joints](concepts/joints/) that Dovetail resolves at build time. No reflection, trimming and Native AOT safe. Reference it, get it Referencing NodaTime, FluentValidation, HotChocolate or a Serilog sink is enough: the matching [integration packages](concepts/integration-packages/) and [templates](concepts/templates/) come with it. C# API reference Every public type of every package, generated from the build: [browse the API](api/).

# Concepts

> The ideas behind LaunchPad and how it builds on Specular and Dovetail.

LaunchPad assembles two libraries into ready-to-use wiring for .NET applications: * [Dovetail](https://rocketsurgeonsguild.github.io/Dovetail/) composes an application at build time from **Joints**, and its SDK works out what kind of application a project is. * [Specular](https://rocketsurgeonsguild.github.io/Specular/) scans assemblies without reflection, so the wiring stays trimming and Native AOT safe. LaunchPad adds the Joints most applications want (health checks, logging, telemetry, validation, time, serialization) and an SDK that picks the right packages for a project. These pages explain the vocabulary the rest of the documentation uses. | Term | In one line | | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | | [Joint](./joints/) | A unit of application wiring that Dovetail resolves and applies at build time. | | [Host model](./host-models/) | The kind of application a project is, decided at build time. It determines which Joints apply. | | [Integration package](./integration-packages/) | A package that adds support for one third-party technology on one surface. | | [Direct reference](./integration-packages/#direct-references) | A reference the project declares itself, as opposed to one it receives transitively. | | [Template](./templates/) | Source written into a project only when its host model and references match. | | [LaunchPad SDK](./launchpad-sdk/) | The MSBuild SDK that chooses LaunchPad packages from what a project references. | | [Operation](./operations/) | A mediator request and its response, exposed over a transport through an operation host. |

# Host models

> The host model is the kind of application a project is, decided at build time from its SDK and references. It determines which Joints apply.

A **host model** is the kind of application a project is. Dovetail’s SDK decides it at build time from the project’s SDK, its `OutputType` and the assemblies it references, and declares it as a `DovetailHost` item. LaunchPad reads that decision to choose packages and [templates](../templates/); nothing about it is decided at run time. | Host model | A project that is… | `ConfigureDovetail()` is generated for | | ----------------- | --------------------------------------------------------------------- | -------------------------------------- | | `HostApplication` | a generic host application: a worker, a console app, a file-based app | `HostApplicationBuilder` | | `WebApplication` | an ASP.NET Core application (`Microsoft.NET.Sdk.Web`) | `WebApplicationBuilder` | | `WebAssembly` | a Blazor WebAssembly application | `WebAssemblyHostBuilder` | | `Maui` | a .NET MAUI application (`UseMaui`) | `MauiAppBuilder` | | `Uno` | an Uno Platform application with the `Hosting` feature | Uno’s `IApplicationBuilder` | A library has no host model. It still exports its Joints, and they apply in every application that references it. ## What the host model decides [Section titled “What the host model decides”](#what-the-host-model-decides) * **Packages.** The [LaunchPad SDK](../launchpad-sdk/) adds `Rocket.Surgery.LaunchPad.Hosting` to any project with a host model, and `Rocket.Surgery.LaunchPad.AspNetCore` to a `WebApplication`. * **Templates.** Each template names the host models it is for. The Serilog console sink Joint, for example, is written into generic host and ASP.NET Core applications, and the browser console Joint only into Blazor WebAssembly ones. * **The entry point.** `ConfigureDovetail()` is generated for the host builder of the project’s host model. Dovetail’s [host reference](https://rocketsurgeonsguild.github.io/Dovetail/reference/dovetail-host/) describes how each one is detected and how to declare one yourself.

# Integration packages

> An integration package adds LaunchPad support for one third-party technology on one surface. The SDK adds them from a project's direct references.

An **integration package** adds LaunchPad support for one third-party technology on one surface. NodaTime has one package for the clock and serialization, `Rocket.Surgery.LaunchPad.NodaTime`, and one for each library it works with: `Rocket.Surgery.LaunchPad.NodaTime.HotChocolate`, `Rocket.Surgery.LaunchPad.NodaTime.StrawberryShake`, `Rocket.Surgery.LaunchPad.NodaTime.EntityFramework` and so on. One technology usually has several. Each package exports the [Joints](../joints/) for its pair of technologies and depends on both. Nothing in it is optional, so a package is tested, versioned and found like any other. The alternative, one package per technology that ships its integrations as templates, was rejected for that reason (see [ADR 0002](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/adr/0002-package-per-integration.md)). The cost is many small packages, which the [LaunchPad SDK](../launchpad-sdk/) chooses for you. ## The packages the SDK chooses [Section titled “The packages the SDK chooses”](#the-packages-the-sdk-chooses) | The project references | The SDK adds | | ------------------------------- | -------------------------------------------------------------------------------------------- | | a [host model](../host-models/) | `Rocket.Surgery.LaunchPad.Hosting` | | the `WebApplication` host model | `Rocket.Surgery.LaunchPad.AspNetCore` | | `NodaTime` | `.NodaTime`, and `.NodaTime.HotChocolate` / `.NodaTime.StrawberryShake` with those libraries | | `NetTopologySuite` | `.Spatial`, and `.StrawberryShake.Spatial` with StrawberryShake | | `FluentValidation` | `.FluentValidation`, and its ASP.NET Core, gRPC, HotChocolate and Blazor packages with those | | `ZeroAlloc.Validation` | the ZeroAlloc ASP.NET Core, gRPC, HotChocolate and Blazor packages with those | | `HotChocolate` | `.HotChocolate` | | `StrawberryShake` | `.StrawberryShake` | | `Grpc.AspNetCore` | `.Grpc` | A file-based app (`dotnet run app.cs`) also gets `Rocket.Surgery.LaunchPad.Foundation` and counts as referencing NodaTime. Each technology can be turned off with its `LaunchPadEnable<Technology>` property, which removes its own package and every integration package it is part of: 
```xml
<PropertyGroup>
  <LaunchPadEnableNodaTime>false</LaunchPadEnableNodaTime>
</PropertyGroup>
```
 The properties are `LaunchPadEnableHosting`, `LaunchPadEnableFoundation`, `LaunchPadEnableAspNetCore`, `LaunchPadEnableNodaTime`, `LaunchPadEnableNetTopologySuite`, `LaunchPadEnableFluentValidation`, `LaunchPadEnableZeroAlloc`, `LaunchPadEnableGrpc`, `LaunchPadEnableHotChocolate` and `LaunchPadEnableStrawberryShake`. ## Direct references [Section titled “Direct references”](#direct-references) A **direct reference** is a package or project reference a project declares itself, as opposed to one it only receives through another package or project. The SDK and the [templates](../templates/) act on direct references only: a library the project receives transitively was chosen by whoever referenced it, not by the project, so it adds nothing to the project. If a technology arrives only transitively and you want its LaunchPad support, reference it directly.

# Joints

> A Joint is a unit of application wiring that Dovetail resolves and applies at build time. LaunchPad ships its wiring as Joints.

A **Joint** is a unit of application wiring: a class that registers services, adds configuration, sets up logging or telemetry, or configures the host. Dovetail’s source generator finds every Joint an application can see, its own and those of the packages and projects it references, orders them, and writes the code that applies them. Nothing is discovered by reflection at run time. LaunchPad used to call these *conventions* (`Rocket.Surgery.Conventions`). Every LaunchPad convention is now a Joint, and the old convention packages are gone. ## What a Joint looks like [Section titled “What a Joint looks like”](#what-a-joint-looks-like) A Joint implements one or more of Dovetail’s Joint interfaces and is marked for export. LaunchPad’s NodaTime package registers the clock this way: 
```csharp
[PublicAPI]
[DovetailExport]
[DovetailCategory(DovetailCategory.Core)]
public class TimeJoint : IServiceJoint, ISetupJoint
{
    public void Register(IDovetailContext context, IServiceCollection services)
    {
        // Try add so that unit tests can insert fakes
        services.TryAddSingleton(TimeProvider.System);
        services.TryAddSingleton<IClock>(SystemClock.Instance);
        services.TryAddSingleton<IDateTimeZoneProvider>(new DateTimeZoneCache(context.Require<NodaTimeOptions>().DateTimeZoneSource));
    }


    void ISetupJoint.Register(IDovetailContext context) => _ = context.GetOrAdd(() => new NodaTimeOptions());
}
```
 * `IServiceJoint` registers services. Other interfaces cover configuration, logging, OpenTelemetry and the host builder. * `ISetupJoint` runs first and puts defaults into the `IDovetailContext`, here the `NodaTimeOptions` an application may override. * `[DovetailExport]` makes the Joint visible to the applications that reference the package. * `[DovetailCategory]` puts the Joint in a category, which is part of its metadata. A Joint that declares none is in the `Application` category; LaunchPad’s foundational Joints, like this one, declare `Core`. ## Applying the Joints [Section titled “Applying the Joints”](#applying-the-joints) An application applies its Joints once, where it builds its host: 
```csharp
var app = await WebApplication.CreateBuilder(args).ConfigureDovetail();
```
 `ConfigureDovetail()` is generated into the application for its [host model](../host-models/). It runs every Joint the application imports, in order, then builds the host. ## Where Joints come from [Section titled “Where Joints come from”](#where-joints-come-from) * **Packages.** Each LaunchPad [integration package](../integration-packages/) exports the Joints for its technology. * **Templates.** Joints that only make sense for some host models, or only when another library is present, are [templates](../templates/) written into the application itself. * **Your own code.** An application or library can define Joints of its own the same way. See [Writing a Joint](../../guides/writing-a-joint/). Dovetail’s documentation covers the Joint interfaces, ordering and the context in depth: [Defining Joints](https://rocketsurgeonsguild.github.io/Dovetail/concepts/defining-joints/).

# LaunchPad SDK

> The MSBuild SDK an application opts into so that the right LaunchPad packages are chosen from what the project references. It builds on Dovetail's SDK.

The **LaunchPad SDK**, `Rocket.Surgery.LaunchPad.Sdk`, is an MSBuild SDK an application opts into so that the right LaunchPad packages are chosen from what the project references. It is the only LaunchPad entry the application needs: no `PackageReference` to LaunchPad or Dovetail. ## How it builds on Dovetail’s SDK [Section titled “How it builds on Dovetail’s SDK”](#how-it-builds-on-dovetails-sdk) The LaunchPad SDK chains `Joinery.Dovetail.Sdk`, so there is no second SDK entry. When a project builds: 1. Dovetail’s SDK decides the project’s [host model](../host-models/) and adds `Joinery.Dovetail.Hosting`, plus `Joinery.Dovetail.Serilog` and `Joinery.Dovetail.OpenTelemetry` when the project references Serilog or OpenTelemetry. LaunchPad turns Serilog on by default. 2. The LaunchPad SDK reads that host model and the project’s [direct references](../integration-packages/#direct-references), and adds the [integration packages](../integration-packages/#the-packages-the-sdk-chooses) that match. 3. NuGet restores everything both SDKs added, so the packages behave like ordinary references. A package the project already references itself is left alone. All of it happens while MSBuild evaluates the project, before restore. Nothing is decided at run time. ## Opting in [Section titled “Opting in”](#opting-in) Name the SDK next to the one the project already uses: 
```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <Sdk Name="Rocket.Surgery.LaunchPad.Sdk" Version="1.0.0" />
</Project>
```
 or make it the project’s SDK (it brings `Microsoft.NET.Sdk` through Dovetail’s): 
```xml
<Project Sdk="Rocket.Surgery.LaunchPad.Sdk/1.0.0">
```
 or apply it to every project in a `Directory.Build.props`, with the version pinned in `global.json`: 
```xml
<Project Sdk="Rocket.Surgery.LaunchPad.Sdk">
```
 
```json
{
    "msbuild-sdks": {
        "Rocket.Surgery.LaunchPad.Sdk": "1.0.0"
    }
}
```
 A file-based app uses the directive form, `#:sdk Rocket.Surgery.LaunchPad.Sdk@1.0.0`, and gets what a console application needs without a `#:package` directive for LaunchPad. [Getting started](../../guides/) walks through each of these. ## Choosing another Dovetail version [Section titled “Choosing another Dovetail version”](#choosing-another-dovetail-version) The SDK chains the Dovetail SDK version it was built with. To chain another, set `LaunchPadDovetailSdkVersion` before the SDK is imported: as a global property, or in a `Directory.Build.props` that sets it and then imports the SDK with `<Import Project="Sdk.props" Sdk="Rocket.Surgery.LaunchPad.Sdk" />`.

# Operations and operation hosts

> An operation is a mediator request exposed over a transport. Operation hosts list the operations a server exposes.

An **operation** is a mediator request, together with its response, that is exposed over one or more transports. `GetRocket.Request` is the same operation whether it is reached as `GET /api/rockets/{id}`, as a gRPC method or as a GraphQL field. On the server, each one reaches its handler through the mediator: `mediator.Send(new GetRocket.Request(id))`. LaunchPad’s API generators write the endpoints, services and resolvers that carry operations. Clients are generated from what those servers describe: their OpenAPI document, GraphQL schema or `.proto`. The [API generators guide](../../guides/api-generators/) shows how to use them; this page explains the vocabulary. ## The pieces [Section titled “The pieces”](#the-pieces) | Term | Meaning | | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | | **Operation** | A mediator request and its response, exposed over a transport. Its name comes from the request: `GetRocket.Request` is `GetRocket`. | | **Contracts project** | The project holding the requests and responses, shared by the servers that expose them. | | **Transport** | A way of carrying an operation: Minimal API, MVC controllers, gRPC or GraphQL. | | **Operation host** | A server type that lists, one by one, the operations it exposes over one transport. | | **Group** | The name a host gives its operations: the middle of their routes, the gRPC package and service. | | **Mediator profile** | How one mediator library shapes requests and dispatches them, so operations work with any mediator. | ## Operation hosts [Section titled “Operation hosts”](#operation-hosts) An operation is reachable only where a host lists it with `[Operation<TRequest>]`: 
```csharp
// A Minimal API host in the web project.
[Operation<GetRocket.Request>]
[Operation<CreateRocket.Request>]
public static partial class RocketsEndpoints;
```
 Referencing a contracts project exposes nothing by itself, and each server shows exactly which operations it exposes. LaunchPad chose this over scanning the contracts for marked requests, which would make every marked request public on every server that references them ([ADR-0003](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/adr/0003-explicit-operation-hosts.md)). The host’s **transport** is inferred from its base type, a transport attribute or its name: `…Endpoints` is Minimal API, `…Controller` is MVC, `…Service` is gRPC and `…Mutations` is GraphQL. The generator writes a complete member for each listed operation and adds whatever else the transport needs on the host. The host also owns the **group**, by default its name without the suffix in kebab-case: `RocketsEndpoints` and `RocketsService` are both `rockets`, so the operations live under `/api/rockets` and in the gRPC service `rockets.Rockets`. ## Clients [Section titled “Clients”](#clients) The generators don’t write clients. A server describes its operations in the transport’s standard format, and a client generator for that format (NSwag or Kiota for OpenAPI, StrawberryShake for GraphQL, Grpc.Tools for a `.proto`) writes the client. A client then needs neither the contracts project nor a mediator, and a route or name the server changes reaches it with the next generated client. ## Mediator profiles [Section titled “Mediator profiles”](#mediator-profiles) Mediator libraries disagree on how a request declares its response and how it is sent. A **mediator profile** describes those shapes, and the generators write code against the profile rather than against one library. LaunchPad has built-in profiles for MediatR, martinothamar/Mediator, ZeroAlloc.Mediator, Immediate.Handlers, Foundatio.Mediator and ChannelMediator, and picks the one the project references. A [custom profile](../../guides/api-generators/#a-custom-profile) covers any other library. The terms on this page are defined in the repository’s [glossary](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/GLOSSARY.md).

# Templates

> A template is source shipped inside a package and written into a consuming project only when its host model and references match, so unused wiring never compiles in.

A **template** is source shipped inside a package, as a `*.cs.template` file, and written into a consuming project only when that project’s [host model](../host-models/) and references match. Unused wiring never compiles in, and the package that ships the template depends on none of the libraries the template uses. `Rocket.Surgery.LaunchPad.Hosting` ships its [Joints](../joints/) this way. Each one is a template with three gates, and every gate has to pass: * **Hosts**: the project declares one of the host models the template is for. * **References**: every assembly the template compiles against is among the project’s references. * **Direct reference**: the project references `Rocket.Surgery.LaunchPad.Hosting` itself (see [direct references](../integration-packages/#direct-references)). A project that only receives the package through a library gets nothing. ## The Hosting templates [Section titled “The Hosting templates”](#the-hosting-templates) | Joint | Written when the project `LaunchPadSerilogConsoleJoint` | `Serilog.Sinks.Console` and `Serilog.Sinks.Async` | generic host, ASP.NET Core | | `LaunchPadSerilogDebugJoint` | `Serilog.Sinks.Debug` and `Serilog.Sinks.Async` | Support for a third-party technology ships as an [integration package](../integration-packages/) instead. The template mechanism itself is Dovetail’s: [Shipping templates](https://rocketsurgeonsguild.github.io/Dovetail/guides/shipping-templates/).

# Getting Started

> Build an application with the LaunchPad SDK, from an empty project to one that applies LaunchPad's Joints.

An application uses LaunchPad through the [LaunchPad SDK](../concepts/launchpad-sdk/). It names the SDK once, and the SDK adds the LaunchPad and Dovetail packages that match the project: its [host model](../concepts/host-models/) and the libraries it references directly. In the snippets, replace `1.0.0` with the version of `Rocket.Surgery.LaunchPad.Sdk` you use. ## A worker or console application [Section titled “A worker or console application”](#a-worker-or-console-application) Add the SDK next to the one the project already names: 
```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>
  <Sdk Name="Rocket.Surgery.LaunchPad.Sdk" Version="1.0.0" />
  <ItemGroup>
    <PackageReference Include="Microsoft.Extensions.Hosting" Version="10.0.14" />
  </ItemGroup>
</Project>
```
 and build the host with `ConfigureDovetail()`, which applies every [Joint](../concepts/joints/) the application imports: 
```csharp
using var host = await Host.CreateApplicationBuilder(args).ConfigureDovetail();
await host.RunAsync();
```
 `ConfigureDovetail()` is generated into the project’s root namespace, so add a `using` for it if `Program.cs` is in another one. The SDK finds a generic host (`HostApplication`) and adds `Joinery.Dovetail.Hosting`, which generates `ConfigureDovetail()`, and `Rocket.Surgery.LaunchPad.Hosting`, whose [templates](../concepts/templates/) bring health checks, logging and telemetry Joints when their libraries are referenced. ## An ASP.NET Core application [Section titled “An ASP.NET Core application”](#an-aspnet-core-application) The same line in a `Microsoft.NET.Sdk.Web` project gives the `WebApplication` host model, which also gets `Rocket.Surgery.LaunchPad.AspNetCore`: 
```xml
<Project Sdk="Microsoft.NET.Sdk.Web">
  <Sdk Name="Rocket.Surgery.LaunchPad.Sdk" Version="1.0.0" />
</Project>
```
 
```csharp
var app = await WebApplication.CreateBuilder(args).ConfigureDovetail();
app.MapHealthChecks("/health");
await app.RunAsync();
```
 ASP.NET Core has the health checks in its shared framework, so `LaunchPadHealthChecksJoint` registers them without another reference. ## Every project in a repository [Section titled “Every project in a repository”](#every-project-in-a-repository) Apply the SDK once in `Directory.Build.props`: 
```xml
<Project Sdk="Rocket.Surgery.LaunchPad.Sdk">
</Project>
```
 and pin its version in `global.json`: 
```json
{
    "msbuild-sdks": {
        "Rocket.Surgery.LaunchPad.Sdk": "1.0.0"
    }
}
```
 Libraries get nothing from the SDK until they reference a technology LaunchPad has a package for: a library has no host model. ## A file-based app [Section titled “A file-based app”](#a-file-based-app) A single `.cs` file run with `dotnet run app.cs` names the SDK with a directive and needs no `#:package` for LaunchPad: 
```csharp
#:sdk Rocket.Surgery.LaunchPad.Sdk@1.0.0
#:property RootNamespace=MyApp


using MyApp;


using var host = await Host.CreateApplicationBuilder(args).ConfigureDovetail();
await host.RunAsync();
```
 It gets the generic host, `Rocket.Surgery.LaunchPad.Foundation`, `Hosting` and `NodaTime`, and Dovetail’s Serilog and OpenTelemetry packages. `RootNamespace` names the namespace `ConfigureDovetail()` is generated in; a file-based app would otherwise take it from the file name. ## Next [Section titled “Next”](#next) * [Choosing integration packages](./choosing-packages/): what the SDK adds for each technology, and how to turn one off. * [Writing a Joint](./writing-a-joint/): add wiring of your own. * The [samples](https://github.com/RocketSurgeonsGuild/LaunchPad/tree/main/sample/Sample.Sdk) consume LaunchPad only through the SDK, the way an application outside the repository does.

# API Generators

> Expose mediator requests as Minimal API, MVC, gRPC and GraphQL endpoints with any of six mediators, and generate clients from their specs.

LaunchPad’s API generators turn mediator requests into a server. You list the requests an **operation host** exposes, and the generator writes the endpoints, each of which sends its request through your mediator. Clients are generated the usual way, from what the server describes: its OpenAPI document, its GraphQL schema or its `.proto`. 
```mermaid
flowchart LR
  subgraph Server application
    A[generated endpoint] --> B["mediator.Send(request)"] --> C[your handler]
  end
  A -. describes .-> D["OpenAPI document · GraphQL schema · .proto"]
  D --> E["generated client (NSwag, Kiota, StrawberryShake, Grpc.Tools, …)"]
  E -- "GET /api/rockets/{id}" --> A
```
 The generators work with MediatR, [martinothamar/Mediator](https://github.com/martinothamar/Mediator), ChannelMediator, Immediate.Handlers, Foundatio.Mediator and ZeroAlloc.Mediator. They are incremental source generators: nothing is found by reflection or by scanning assemblies, and the generated Minimal API endpoints are native AOT safe. This page covers the Minimal API, MVC controller, gRPC and GraphQL (mutations) servers, and generating clients for them. ## Packages [Section titled “Packages”](#packages) The generators ship in `Rocket.Surgery.LaunchPad.Foundation`, next to LaunchPad’s other source generators, so a project that references Foundation has them: the attributes (`[ApiOperation]`, `[Operation<T>]`, …), host checks, code fixes, and the generators for Minimal API (`*Endpoints`), MVC (`*Controller`), gRPC (`*Service`) and GraphQL (`*Mutations`). Reference Foundation from the servers and from contracts that customise their operations. The attributes are generated into each project that uses them, as `internal` types, so nothing reaches your runtime dependencies. One generator per transport runs in every project that references Foundation, and each writes code only for the hosts of its kind, using that transport’s library (ASP.NET Core, protobuf-net.Grpc or HotChocolate). Why they share Foundation’s analyzer is recorded in [ADR 0004](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/adr/0004-one-generator-assembly.md). ## Quick start [Section titled “Quick start”](#quick-start) **Contracts**: plain mediator requests. Nothing is required: XML documentation becomes the OpenAPI summary, `[ApiOperation]` adds metadata to the operation, and `[Creates]` marks a response that identifies a new resource. 
```csharp
namespace Rockets.Contracts;


public static class GetRocket
{
    /// <summary>Load a rocket.</summary>
    public sealed record Request(Guid Id) : IRequest<RocketModel?>;
}


public static class CreateRocket
{
    public sealed record Request(string Name) : IRequest<Response>;


    [Creates(typeof(GetRocket.Request))]   // answers 201 with a Location for GetRocket
    public sealed record Response(Guid Id);
}
```
 **Server**: a `static partial` class named `*Endpoints`, one attribute per operation. 
```csharp
[Operation<GetRocket.Request>]
[Operation<ListRockets.Request>]
[Operation<CreateRocket.Request>]
[Operation<EditRocket.Request>]
[Operation<DeleteRocket.Request>]
public static partial class RocketsEndpoints;


// Program.cs
builder.Services.AddOpenApi();
app.MapOpenApi();            // /openapi/v1.json, for the clients
app.MapRocketsEndpoints();   // returns the RouteGroupBuilder for /api/rockets
```
 **Client**: generated from the server’s OpenAPI document by the tool of your choice. See [Generating clients](#generating-clients). ## Operation hosts [Section titled “Operation hosts”](#operation-hosts) An operation host is a top-level `partial` type. The generator writes complete members into it, with signatures it chooses. A host lists every operation it exposes, so nothing becomes public by accident ([ADR-0003](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/adr/0003-explicit-operation-hosts.md)). The transport comes from the host itself; the first rule that matches wins: | The host… | Transport | | ---------------------------------------------- | ------------------------ | | derives from `ControllerBase` | MVC controller | | has `[ExtendObjectType(Query)]` / `(Mutation)` | GraphQL query / mutation | | is named `*Controller` | MVC controller | | is named `*Endpoints` or `*Api` | Minimal API | | is named `*Service` | gRPC server | | is named `*Queries` / `*Mutations` | GraphQL | A host that matches nothing, or whose transport’s library isn’t referenced, is LPAD1017. A Minimal API host must be `static partial` and any other host `partial`; LPAD1010 has a code fix that adds the modifiers. ### Names, groups and routes [Section titled “Names, groups and routes”](#names-groups-and-routes) * The **operation name** comes from the request: `GetRocket.Request` and `GetRocketRequest` are both `GetRocket`. A nested type named only by a verb takes its container’s noun: `EditRocket.PatchRequest` is `PatchRocket`. The name is the endpoint name and OpenAPI operation id, the gRPC method and (camelCased) the GraphQL field, so it’s also the method name in generated clients. * The **group** is the host name without its suffix, in kebab-case: `RocketsEndpoints` and `RocketsService` are both `rockets`. Set `[OperationHost(Group = "...")]` to choose another. * The **route** is `RoutePrefix / group / path`. The prefix defaults to `api`. The path is REST style: the verb prefix and the group noun are dropped from the operation name, and `{id}` comes first when the request has an `Id`. Tokens get the constraint of their member’s type (`{id:guid}` for a `Guid`, or for a strongly typed id whose `Value` is one); a `Route` you write is used as written. | Operation (group `rockets`) | Verb and route | Success | | --------------------------- | -------------------------------------- | ------- | | `ListRockets` | `GET /api/rockets` | 200 | | `GetRocket` | `GET /api/rockets/{id}` | 200 | | `CreateRocket` | `POST /api/rockets` | 201 | | `EditRocket` | `PUT /api/rockets/{id}` | 200 | | `PatchRocket` | `PATCH /api/rockets/{id}` | 200 | | `DeleteRocket` | `DELETE /api/rockets/{id}` | 204 | | `GetRocketLaunchRecords` | `GET /api/rockets/{id}/launch-records` | 200 | Verbs come from the name’s prefix: `Get`/`Find`/`List`/`Search`… are GET, `Create`/`Add`/`New`… are POST (201), `Edit`/`Update`/`Save`… are PUT, `Patch` is PATCH, `Delete`/`Remove`/`Cancel`… are DELETE (204), and anything else is POST. Two operations with the same verb and route are LPAD1008. ### Customising an operation [Section titled “Customising an operation”](#customising-an-operation) Named arguments on `[Operation<T>]` win over `[ApiOperation]` on the request, which wins over the rules above: 
```csharp
[OperationHost(Group = "fleet", RoutePrefix = "api/v2")]
[Operation<SearchRockets.Request>(Policy = new[] { "rockets.read" }, Summary = "Search")]
[Operation<LaunchRocket.Request>(Route = "{id}/launch", Roles = new[] { "pilot" })]
public static partial class FleetEndpoints
{
    // Optional hooks, one per operation; unimplemented ones compile away.
    static partial void ConfigureSearchRockets(IEndpointConventionBuilder endpoint) => endpoint.CacheOutput();
}
```
 | On `[Operation<T>]` | Effect | | ------------------------------------------------------------ | ----------------------------------------------------------------------------------- | | `Route`, `Verb`, `Name` | Override the path, verb and endpoint name. | | `Summary`, `Description`, `Tags` | OpenAPI metadata. | | `Policy`, `Roles`, `AuthenticationSchemes`, `AllowAnonymous` | Authorization on the endpoint. | | `Input` | Bind a transport-specific input type and convert it with its `Create()` (LPAD1020). | | `Version` | The API version of the operation, overriding the host’s (see below). | `[Creates(typeof(TRequest))]` (or `[Creates<TRequest>]` where generic attributes are available) on a response type makes every operation that returns it answer `201 Created`, with a `Location` header for `TRequest`’s GET operation, filled from the response’s members (`CreateRocket.Response.Id` → `{id}`). The target is looked for on the same host first, then on any other host of the same transport. When no host exposes it, or a route value has no matching member, the operation still answers 201, without a `Location`, and LPAD1023 says why. Summaries and descriptions come from, in order: the operation’s `Summary`/`Description`, `[ApiOperation]`, and the `<summary>`/`<remarks>` of the request type or of the type that contains it (`GetRocket` for `GetRocket.Request`). For a request in a referenced project, the base package’s build targets hand that project’s XML documentation file to the generators, so turn on `GenerateDocumentationFile` there. A contracts package can be added with `<AdditionalFiles Include="path/to/Contracts.xml" LaunchPadApiDocumentation="true" />`. ### API versions [Section titled “API versions”](#api-versions) `[OperationHost(Version = "1.0")]` gives every operation of the host an API version, and `[Operation<T>(Version = "2.0")]` overrides it for one operation. The server maps them with [Asp.Versioning](https://github.com/dotnet/aspnet-api-versioning); clients send the version in the `api-version` query string, Asp.Versioning’s default reader. 
```csharp
[OperationHost(Version = "1.0")]
[Operation<GetRocket.Request>(Version = "2.0")]
[Operation<CreateRocket.Request>]
public static partial class RocketsEndpoints;


builder.Services.AddApiVersioning();
app.MapRocketsEndpoints();
```
 * **Minimal API** hosts build one version set from the versions of their operations and map each endpoint to its own version (`WithApiVersionSet`, `MapToApiVersion`). Reference `Asp.Versioning.Http` and call `AddApiVersioning()`. * **Controller** hosts get an `[ApiVersion]` per version on the class and `[MapToApiVersion]` on each action. Reference `Asp.Versioning.Mvc` and call `AddApiVersioning().AddMvc()`. A request for a version the endpoint isn’t mapped to, or with no version, answers 400 with Asp.Versioning’s problem details. To accept unversioned requests, set `AssumeDefaultVersionWhenUnspecified` and `DefaultApiVersion` in `AddApiVersioning(options => ...)`. Without the package for the host’s transport (`Asp.Versioning.Http` for Minimal API, `Asp.Versioning.Mvc` for controllers), versions aren’t mapped and LPAD1024 warns. gRPC and GraphQL hosts have no API versions; `Version` on them is LPAD1021. ### MVC controllers [Section titled “MVC controllers”](#mvc-controllers) A `partial` class named `*Controller` (or deriving from `ControllerBase`) gets one action per operation, on the same routes as a Minimal API host would: 
```csharp
[Operation<GetRocket.Request>]
[Operation<CreateRocket.Request>]
public partial class RocketsController;   // → [ApiController, Route("api/rockets")] RocketsController : ControllerBase


// Program.cs
builder.Services.AddControllers();
app.MapControllers();
```
 * The generator adds `[ApiController]`, `[Route("{RoutePrefix}/{Group}")]` and the `ControllerBase` base only when the host doesn’t declare them. A host’s own `[Route]` replaces prefix and group (`[controller]` is the host’s noun), and its hand-written actions, filters and attributes stay as they are. * Actions return MVC results, so responses use MVC’s formatters and `AddJsonOptions` settings, and carry `[ProducesResponseType]` for ApiExplorer. Binding failures answer 400 through `[ApiController]`. * The mediator is resolved inside the action, so the host’s constructor is yours. * MVC only discovers `public` controllers. ### gRPC [Section titled “gRPC”](#grpc) A `partial` class named `*Service` becomes a code-first gRPC service with [protobuf-net.Grpc](https://protobuf-net.github.io/protobuf-net.Grpc/). The generator writes its contract too (a `[Service]` interface, one operation per request), so the contracts project needs no gRPC reference. 
```csharp
[Operation<GetRocket.Request>]
[Operation<ListRockets.Request>]
public partial class RocketsService;


builder.Services.AddCodeFirstGrpc();
app.MapRocketsService();


// With protobuf-net.Grpc.Reflection referenced: the .proto to generate clients from.
File.WriteAllText("rockets.proto", RocketsService.GetProto());
```
 * The service is `{package}.{Service}`: the group as the package and in PascalCase as the service, so `rockets.Rockets` and routes such as `/rockets.Rockets/GetRocket`, whatever the server’s C# namespace. * The whole request is the message: route, query and header binding don’t apply. * Requests and responses need `[DataContract]` with ordered `[DataMember]`s, or `[ProtoContract]` (LPAD1014). Positional records work: the generated code lets protobuf-net create them without a parameterless constructor. * Nested types are named with their container (`CreateRocketRequest`), so the many `X.Request` types don’t all become `message Request`. * Messages use protobuf-net’s compatibility level 300: a `Guid` or `decimal` travels as a `string`, a `DateTime` as `google.protobuf.Timestamp` and a `TimeSpan` as `google.protobuf.Duration`, the types a `.proto` declares, not protobuf-net’s `bcl.proto` messages. * protobuf-net.Grpc only carries classes. A struct request or response (ZeroAlloc’s requests) goes in a wrapper the generator writes, which protobuf-net replaces by the struct itself on the wire, so its message is the struct’s. A primitive response (`bool`) travels in a one-field message. Void operations answer `google.protobuf.Empty`. * A `null` response answers `NotFound`. Streams are server streaming. * `GetProto()` is generated when the server references `protobuf-net.Grpc.Reflection`. ### GraphQL mutations [Section titled “GraphQL mutations”](#graphql-mutations) A `partial` class named `*Mutations` (or with `[ExtendObjectType(OperationTypeNames.Mutation)]`) gets one HotChocolate mutation per operation, taking the request as its single `request` argument: 
```csharp
[ExtendObjectType(OperationTypeNames.Mutation)]
[Operation<CreateRocket.Request>]
[Operation<EditRocket.PatchRequest>(Input = typeof(EditRocketPatchRequest))]
[Operation<DeleteRocket.Request>]
public partial class RocketMutation;


builder.Services.AddGraphQLServer().AddQueryType().AddMutationType().AddRocketMutation();
// mutation { createRocket(request: { name: "Falcon" }) { id } }
```
 * Field names are the operation names in camelCase, or `[ApiOperation(GraphQLName)]`. A field declared on two mutation hosts is LPAD1009. * `Add{Host}()` names nested inputs and responses after their container (`CreateRocketRequest`, `CreateRocketResponse`), so the many nested `Request` types don’t collide; other inputs keep HotChocolate’s `…Input` names. LaunchPad.HotChocolate’s `NestedTypeNameTypeInterceptor` leaves those names as they are. * A void operation answers `Boolean!` (`true`). A stream isn’t a mutation (LPAD1015, skipped). * An operation is a mutation unless its verb is GET; one inferred as a query on a mutation host is LPAD1019. Set `[ApiOperation(GraphQLOperation = GraphQLOperation.Mutation)]` to keep it. * `Input` types work as on HTTP. An input implementing LaunchPad’s `IOptionalTracking<TRequest>` gets its `Create()` from another generator, which counts. * The summary (or XML documentation) is the field’s description; `Policy`, `Roles` and `AllowAnonymous` become HotChocolate authorization. **Queries aren’t generated.** They usually return `IQueryable` with paging, filtering and projections, which a mediator response can’t; a `*Queries` host is LPAD1017. Write queries by hand. ## Binding and responses [Section titled “Binding and responses”](#binding-and-responses) * Route tokens bind to the request member of the same name; a token without a member is LPAD1003, an `[ApiRoute]` member missing from the route is LPAD1004. * GET and DELETE take the other members from the query string; complex members there are LPAD1005. POST, PUT and PATCH take the whole request as the JSON body, and route values are applied on top (`request with { Id = id }` for records). * Route, query and header values must be parsable: primitives, enums, `Guid`, date and time types, or anything with `IParsable<T>` or a static `TryParse` (LPAD1007). Strongly typed IDs work when they provide one. * `[ApiQuery]`, `[ApiHeader]`, `[ApiBody]`, `[ApiService]` and `[ApiIgnore]` on a member override the defaults; ASP.NET Core’s `[FromRoute]` and friends are honoured too. | Response | Server answers | | --------------------- | ------------------------------------------------------------------------------------ | | `T` | 200 (201 for creates) with JSON | | `T?` | the value, or 404 for `null` | | none / `Unit` | 204 | | `IAsyncEnumerable<T>` | newline-delimited JSON (`application/x-ndjson`), one item per line, flushed per item | | a union | its value case as above, each error case as a problem (see below) | A binding failure answers 400, with a ProblemDetails body when the application calls `AddProblemDetails()`. Generated endpoints describe their parameters, bodies and responses to ApiExplorer, so OpenAPI documents them like hand-written ones. ### Union responses [Section titled “Union responses”](#union-responses) A handler can return a union response, its value case and its error cases, instead of throwing (ADR-0006). A union is a C# 15 union: a `union` declaration, LaunchPad’s portable `[Union] partial struct` (see the [union types design](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/design/union-types.md)), or the same shape written by hand. The generators know it by `System.Runtime.CompilerServices.UnionAttribute` or `IUnion`. Its case types are the parameter types of its public one-parameter constructors. An error case is known by its name or by `[ApiError]`; the value case is the first case that is neither, and a union has exactly one. LaunchPad’s standard problem cases in `Rocket.Surgery.LaunchPad.Primitives` (`NotFound`, `Invalid`, `UnprocessableEntity`, `Unauthorized`, `Forbidden`, `Conflict`) match the name rules below. A union may list `Problem` itself as a case: it answers each standard case by its runtime type, and any other problem as 500. A problem’s detail, title, link, instance and properties fill the transport’s error shape (below). 
```csharp
public sealed record RocketNotFound(Guid Id);
[ApiError(422, GrpcStatus = 9, GraphQLCode = "UNPROCESSABLE")] public sealed record NotReady(string Reason);


public union LaunchRocketResult(RocketModel, RocketNotFound, NotReady);
public static class LaunchRocket { public sealed record Request(Guid Id) : IRequest<LaunchRocketResult>; }
```
 The value case answers like a plain response: 200, 201 with `[Creates]`, 204 for a unit (`Unit`, `ValueTuple`), 404 when it or the union (`LaunchRocketResult?`) is nullable and null. An error case’s status comes from `[ApiError]` on its type, or else from its name, ignoring an `Error`, `Exception`, `Problem`, `Failure` or `Result` ending: | Name starts or ends with | HTTP | gRPC | GraphQL code | | ----------------------------------- | ---- | -------------------- | ----------------- | | `NotFound` | 404 | `NotFound` | `NOT_FOUND` | | `Unauthorized`, `Unauthenticated` | 401 | `Unauthenticated` | `UNAUTHENTICATED` | | `Forbidden` | 403 | `PermissionDenied` | `FORBIDDEN` | | `Conflict` | 409 | `FailedPrecondition` | `CONFLICT` | | `Validation`, `UnprocessableEntity` | 422 | `InvalidArgument` | `BAD_USER_INPUT` | | `Invalid` | 400 | `InvalidArgument` | `BAD_USER_INPUT` | `[ApiError(statusCode)]` sets the HTTP status; its gRPC status and GraphQL code default to the ones for that status. A second case that matches no name and has no `[ApiError]` is LPAD1028. Each transport carries the case name, so cases that share a status stay distinct: * **HTTP**: ProblemDetails (`application/problem+json`) with the status, the case name in a `case` extension and the case’s members as camel-cased extensions; a problem’s detail, title, link (as `type`) and instance fill those fields and its properties are extensions. Each status is described in OpenAPI as a ProblemDetails response; a schema per case is planned with the OpenAPI transformers (#3149). * **gRPC**: an `RpcException` with the status, the case name in the `case` trailer and the case, serialized by protobuf-net, in the `case-bin` trailer (left out for a case without members). A problem’s detail is the status message and it has no `case-bin`. A case with members needs `[DataContract]` or `[ProtoContract]` (LPAD1014), and `GetProto()` declares its message. * **GraphQL**: an error whose `extensions.code` is the code from the table (or `[ApiError(GraphQLCode)]`), with the case name in `extensions.case` and the case’s members as extensions. A problem’s detail is the error message and its properties are extensions. The codes follow the convention most GraphQL servers and clients use. A stream of unions (`IAsyncEnumerable<LaunchRocketResult>`) streams its value cases and ends with the first error case: over HTTP, as the response’s ProblemDetails when nothing was written yet, otherwise as a last NDJSON line holding the problem; over gRPC, as the `RpcException` above. GraphQL hosts skip streams (LPAD1015). `NotFoundException` and a `null` response keep answering 404 for handlers that don’t return a union. ## Generating clients [Section titled “Generating clients”](#generating-clients) The generators don’t write clients. Each server describes itself in a standard format, and any client generator for that format works: | Server | Spec | Client generators | | ----------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------- | | Minimal API | OpenAPI: `AddOpenApi()` and `MapOpenApi()` (Microsoft.AspNetCore.OpenApi) | NSwag, Kiota, OpenAPI Generator, Refitter, … | | Controllers | OpenAPI, the same way | the same | | gRPC | `.proto`: `{Host}.GetProto()` | Grpc.Tools (`<Protobuf GrpcServices="Client" />`), any protoc plugin | | GraphQL | SDL: HotChocolate serves it at `/graphql?sdl` | StrawberryShake, graphql-codegen, … | Write the spec at build or in CI, for example from a small console app or test that starts the server with `TestServer` and saves `/openapi/v1.json`, `/graphql?sdl` and `GetProto()`, then point the client generator at the files. LaunchPad’s own functional tests do that (`test/Api/Functional/Clients`): NSwag, Grpc.Tools and StrawberryShake clients, generated from the specs on every build. Things to know: * **Nested request types.** Microsoft.AspNetCore.OpenApi names a schema after the type’s simple name, so `GetRocket.Request` and `CreateRocket.Request` would both be `Request`. Name them with their container: 
  ```csharp
  builder.Services.AddOpenApi(options => options.CreateSchemaReferenceId = type =>
      type.Type.DeclaringType is { } outer && !type.Type.IsGenericType
          ? outer.Name + type.Type.Name
          : OpenApiOptions.CreateDefaultSchemaReferenceId(type));
  ```
 * **Streams.** OpenAPI documents a stream as `application/x-ndjson`, which most generated clients don’t read: they expect one JSON array. Read the response yourself, one JSON item per line. * **Struct requests.** System.Text.Json builds a struct through its parameterless constructor, so OpenAPI doesn’t mark its positional members required the way it does a record class’s. Add `[Required]` to keep generated clients non-nullable. * **StrawberryShake** declares a local named `request` in each generated operation, so a variable named `$request` doesn’t compile (CS0136). Name the variable something else: `mutation CreateRocket($rocket: CreateRocketRequest!) { createRocket(request: $rocket) { id } }`. ## Mediator profiles [Section titled “Mediator profiles”](#mediator-profiles) The generators find your mediator from the libraries the project references. Exactly one of the built-in profiles must match, or you declare one (LPAD1002): | Mediator | Requests | Server dispatches through | | ---------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------- | | MediatR | `IRequest<T>`, `IRequest`, `IStreamRequest<T>` | `ISender` | | martinothamar/Mediator | `IRequest<T>`, `ICommand<T>`, `IQuery<T>`, `ICommand` and stream variants | `ISender` | | ChannelMediator | `IRequest<T>`, `IRequest`, `IStreamRequest<T>` | `IMediator` | | Immediate.Handlers | anything; the response comes from the `[Handler]` (a bare `ValueTask` is void) or `[ApiOperation(Response)]` | `IHandler<TRequest, TResponse>` | | Foundatio.Mediator | optional `IRequest<T>`/`ICommand<T>`/`IQuery<T>`, or `ICommand` for void, else `[ApiOperation(Response)]` | `IMediator.InvokeAsync` | | ZeroAlloc.Mediator | `IRequest<T>`, `IRequest`, `IStreamRequest<T>` | its generated `IMediator` | Requests that implement no marker interface (Immediate.Handlers, and optionally Foundatio) name their response with `[ApiOperation(Response = typeof(...))]`. `typeof` can’t say “nullable”, so for Immediate.Handlers the server takes the nullability from its `[Handler]` method when that is next to the request or the host. ### A custom profile [Section titled “A custom profile”](#a-custom-profile) Another mediator can be described with two assembly attributes: 
```csharp
[assembly: MediatorProfile(SenderType = typeof(IMyDispatcher), SendMethod = "Dispatch", StreamMethod = "Stream", Name = "MyMediator")]
[assembly: MediatorRequest(typeof(IMyRequest<>), HandlerInterface = typeof(IMyHandler<,>), HandleMethod = "Handle")]
[assembly: MediatorRequest(typeof(IMyStream<>), Kind = RequestKind.Stream)]
```
 A profile without a `SenderType` dispatches through each request kind’s `HandlerInterface`. An operation the profile can’t dispatch is skipped (LPAD1016). ## Patch operations [Section titled “Patch operations”](#patch-operations) A patch operation’s request carries only the changes to another operation’s request: it implements `IPropertyTracking<TRequest>`, and the property tracking generator gives it an `Assigned<T>` member for each property of `TRequest` and an `ApplyChanges` method. Its handler is generated too. Declare the handler class `partial`, with the mediator’s handler interface and the services it needs, including the mediator’s sender, and implement `GetRequest`, which loads the current request: 
```csharp
public partial record PatchRequest : IRequest<RocketModel>, IPropertyTracking<Request>
{
    public RocketId Id { get; init; }
}


internal partial class EditRocketHandler(RocketDbContext dbContext, IMediator mediator)
    : IRequestHandler<Request, RocketModel>, IRequestHandler<PatchRequest, RocketModel>
{
    public async ValueTask<RocketModel> Handle(Request request, CancellationToken cancellationToken) => /* ... */;


    private partial async ValueTask<Request> GetRequest(PatchRequest request, CancellationToken cancellationToken) =>
        MapRequest(await dbContext.Rockets.FindAsync([request.Id], cancellationToken) ?? throw new NotFoundException());
}
```
 The generated handle method applies the patch to that request and sends the result through the mediator, so the full request is validated like any other. The handle method’s shape (`Task<T>` or `ValueTask<T>`, the cancellation token) comes from the mediator’s handler interface, and the handler interface is written in your source, so a mediator’s own source generator (Mediator, ZeroAlloc.Mediator) still finds the handler. A profile without a sender (Immediate.Handlers) can’t send the patched request (LPAD1025). ## Native AOT [Section titled “Native AOT”](#native-aot) Generated Minimal API endpoints don’t rely on the Request Delegate Generator (which can’t see generated code): they parse route, query and header values, read the body and write the result through the application’s `JsonTypeInfo`. A native AOT application supplies a `JsonSerializerContext`: 
```csharp
builder.Services.AddJsonTypeInfoResolver(RocketsJsonContext.Default);
// or, without LaunchPad's SystemTextJsonJoint:
builder.Services.ConfigureHttpJsonOptions(o => o.SerializerOptions.TypeInfoResolverChain.Insert(0, RocketsJsonContext.Default));
```
 LaunchPad’s nested `X.Request` types share a simple name, so each `[JsonSerializable]` entry needs its own `TypeInfoPropertyName`; without it, SYSLIB1031 silently skips the type. In a project that sets `PublishAot`, `IsAotCompatible`, `PublishTrimmed` or `IsTrimmable` (or `LaunchPadApiRequireJsonContext`), LPAD1030 names each body and response type no context in the project or its references declares, or reaches through its properties and collections. See [JSON and native AOT](../json-and-native-aot/). In an AOT application, `Configure{Operation}` receives an `IEndpointConventionBuilder`, and endpoint filters don’t apply. `test/Api/Aot` publishes such a server with `PublishAot` and checks it with a round trip over HTTP. ## Diagnostics [Section titled “Diagnostics”](#diagnostics) | ID | Severity | Meaning | | -------- | -------- | ----------------------------------------------------------------------------------------------------- | | LPAD1001 | Error | The request matches no request kind of the profile and has no `Response`. | | LPAD1002 | Error | No mediator profile, or several built-in ones match. | | LPAD1003 | Error | A route token has no matching member. | | LPAD1004 | Error | An `[ApiRoute]` member isn’t in the route. | | LPAD1005 | Error | A complex member is bound from the route or query string. | | LPAD1006 | Error | The request can’t be built from the bound values. | | LPAD1007 | Error | A route, query or header member isn’t parsable. | | LPAD1008 | Error | Two operations share a verb and route. | | LPAD1009 | Error | A GraphQL field is declared on two mutation hosts. | | LPAD1010 | Error | The host isn’t `partial` (Minimal API: `static partial`). Has a code fix. | | LPAD1014 | Warning | A gRPC request or response has no `[DataContract]` or `[ProtoContract]`. | | LPAD1015 | Warning | A stream operation on a GraphQL host is skipped. | | LPAD1016 | Info | An operation is skipped because the profile can’t dispatch it. | | LPAD1017 | Error | The host’s transport can’t be inferred, or its library isn’t referenced. | | LPAD1019 | Error | A query operation is listed on a mutation host. | | LPAD1020 | Error | An `Input` type has no parameterless `Create()` returning the request. | | LPAD1021 | Warning | An `[OperationHost]` setting doesn’t apply to the host’s transport. | | LPAD1023 | Warning | A `[Creates]` response has no reachable location target; it answers 201 without a `Location`. | | LPAD1024 | Warning | An operation has an API version, but the server lacks the Asp.Versioning package for its transport. | | LPAD1025 | Error | A patch handler has no constructor parameter, field or property of the mediator’s sender type. | | LPAD1026 | Error | A patch handler is nested in a type that isn’t `partial`. | | LPAD1027 | Error | A patch handler’s interface doesn’t return `Task<T>` or `ValueTask<T>`. | | LPAD1028 | Error | A union has a case besides its value case that has no status: no name rule and no `[ApiError]`. | | LPAD1030 | Warning | A trimmed or AOT project has a Minimal API body or response type no `JsonSerializerContext` declares. | LPAD1011, LPAD1012, LPAD1013, LPAD1018 and LPAD1022 belonged to the generated clients, which were removed; the IDs aren’t reused. ## Limitations [Section titled “Limitations”](#limitations) * The generators don’t configure Asp.Versioning’s reader: versions are read from the `api-version` query string unless you configure it. * With Foundatio, give each request its own handler class: Foundatio’s generator names its wrappers after the message’s simple name, which nested `X.Request` types share.

# Choosing integration packages

> Turn on LaunchPad support for a technology by referencing it, see what the SDK added, and opt a project out.

With the [LaunchPad SDK](../../concepts/launchpad-sdk/) a project turns on LaunchPad support for a technology by referencing the technology itself. There is no LaunchPad package to look up: the SDK adds the [integration packages](../../concepts/integration-packages/) that match. ## Turning a technology on [Section titled “Turning a technology on”](#turning-a-technology-on) Reference the library directly from the project that uses it: 
```xml
<ItemGroup>
  <PackageReference Include="NodaTime" Version="3.3.7" />
  <PackageReference Include="HotChocolate.AspNetCore" Version="15.1.20" />
</ItemGroup>
```
 This project gets `Rocket.Surgery.LaunchPad.NodaTime`, `Rocket.Surgery.LaunchPad.HotChocolate` and, because it has both, `Rocket.Surgery.LaunchPad.NodaTime.HotChocolate`. The table of what each technology adds is in [Integration packages](../../concepts/integration-packages/#the-packages-the-sdk-chooses). Only [direct references](../../concepts/integration-packages/#direct-references) count. If NodaTime reaches the project only through another library, the project gets no NodaTime package; reference NodaTime itself to get one. ## Seeing what was added [Section titled “Seeing what was added”](#seeing-what-was-added) The packages the SDK adds are ordinary `PackageReference` items marked `IsImplicitlyDefined`, so they show up in `dotnet list package` and in the IDE’s dependencies like any other. A package the project references itself is left as the project wrote it, which is also how to pin one to another version. ## Turning a technology off [Section titled “Turning a technology off”](#turning-a-technology-off) Set the technology’s `LaunchPadEnable<Technology>` property to `false`. That removes its own package and every integration package it is part of: 
```xml
<PropertyGroup>
  <!-- keeps NodaTime, drops Rocket.Surgery.LaunchPad.NodaTime and Rocket.Surgery.LaunchPad.NodaTime.HotChocolate -->
  <LaunchPadEnableNodaTime>false</LaunchPadEnableNodaTime>
</PropertyGroup>
```
 `LaunchPadEnableHosting` and `LaunchPadEnableAspNetCore` turn off the packages that come with the host model. Dovetail’s own packages have properties of their own, such as `DovetailEnableSerilog` and `DovetailEnableOpenTelemetry`. ## Logging and telemetry sinks [Section titled “Logging and telemetry sinks”](#logging-and-telemetry-sinks) Serilog sinks and enrichers and OpenTelemetry instrumentations are chosen the same way: reference the package, and the [template](../../concepts/templates/) that turns it on is written into the application. 
```xml
<ItemGroup>
  <PackageReference Include="Serilog.Sinks.Console" Version="6.1.1" />
  <PackageReference Include="Serilog.Sinks.Async" Version="2.1.0" />
  <PackageReference Include="OpenTelemetry.Instrumentation.AspNetCore" Version="1.20.1" />
</ItemGroup>
```
 gives an ASP.NET Core application `LaunchPadSerilogConsoleJoint` and `LaunchPadAspNetCoreInstrumentationJoint`.

# JSON and native AOT

> Give LaunchPad the System.Text.Json metadata of your types with a source generated context, so the application trims and publishes with native AOT.

LaunchPad reads and writes JSON only with the JSON contexts it is given, never through reflection, in a JIT application as much as in a trimmed or native AOT one ([ADR 0007](https://github.com/RocketSurgeonsGuild/LaunchPad/blob/main/docs/adr/0007-no-json-reflection.md)). Every type that crosses the wire needs metadata from a source generated `JsonSerializerContext`, and a missing one fails during development rather than after publishing. ## The generated JSON context [Section titled “The generated JSON context”](#the-generated-json-context) An executable project (a console or worker app, or an ASP.NET Core one) that references Rocket.Surgery.LaunchPad.Primitives gets a JSON context written for it before it compiles. Every library that references Primitives lists, in its assembly, the types of it that cross the wire as JSON: * every mediator request, with its response or stream item type, * every `IPropertyTracking<T>` patch type, with its target, * every type marked `[IncludeInJsonContext]`. The application’s build reads those lists from its referenced assemblies and writes `LaunchPadJsonContext` (in the project’s root namespace), with a `[JsonSerializable]` for each type, and a Joint that chains it into the application’s JSON options. Nothing needs wiring. The context is written as source, not by a generator, because generators can’t see each other’s output: the System.Text.Json source generator would never see a context another generator wrote. And it names types from referenced assemblies, because their metadata is complete. A type compiled in the same project as the context only has the members its source declares, not the ones other generators add to it (property tracking, `[InheritFrom]`). So keep operations in a contracts or core project. Requests declared in the application itself are still reported by LPAD1030. | Property | Default | Meaning | | ------------------------------- | ------------------------------------------- | ------------------ | | `LaunchPadGenerateJsonContext` | `true` in executables, not in test projects | Write the context. | | `LaunchPadJsonContextName` | `LaunchPadJsonContext` | The class name. | | `LaunchPadJsonContextNamespace` | `$(RootNamespace)` | The namespace. | ## Chaining a context of your own [Section titled “Chaining a context of your own”](#chaining-a-context-of-your-own) For types the generated context doesn’t cover, declare a context and register it, in a [Joint](../../concepts/joints/) or in the host’s services: 
```csharp
[JsonSerializable(typeof(RocketModel))]
[JsonSerializable(typeof(CreateRocket.Request), TypeInfoPropertyName = "CreateRocketRequest")]
[JsonSerializable(typeof(CreateRocket.Response), TypeInfoPropertyName = "CreateRocketResponse")]
public partial class RocketsJsonContext : JsonSerializerContext;


services.AddJsonTypeInfoResolver(RocketsJsonContext.Default);
```
 `SystemTextJsonJoint` (in `Rocket.Surgery.LaunchPad.Primitives`) builds the `TypeInfoResolverChain` of every `JsonSerializerOptions` the service provider creates from the registered resolvers. `SystemJsonTextJoint` (in `Rocket.Surgery.LaunchPad.AspNetCore`) copies those options into the ASP.NET Core HTTP and MVC JSON options, so a context registered once reaches Minimal APIs, controllers, problem details and the generated API endpoints. The chain, first to last: 1. The application’s resolvers (`order` 0, the default), in the order they were added. A resolver added twice is chained once. 2. LaunchPad’s own resolvers (`JsonTypeInfoResolverRegistration.LibraryOrder`): the primitive and `object` values LaunchPad writes (problem details properties, health check data), the FluentValidation problem details, and the NodaTime and NetTopologySuite types, which resolve from the converters their packages add. The first resolver that knows a type wins, so an application can take over any type LaunchPad resolves. LaunchPad adds no reflection based resolver: a type no JSON context knows throws `NotSupportedException`. An application that wants reflection adds `DefaultJsonTypeInfoResolver` to the chain itself, and LaunchPad leaves it there. ASP.NET Core’s own HTTP and MVC JSON options keep the reflection resolver ASP.NET adds to a JIT application; LaunchPad’s resolvers go in front of it. ## Types written by a converter [Section titled “Types written by a converter”](#types-written-by-a-converter) A converter in `JsonSerializerOptions.Converters` handles a type, but a resolver still has to hand out its metadata when the type is serialized at the root or as an `object`. `JsonConverterTypeInfoResolver` builds it from the converter, without reflection: 
```csharp
services.AddJsonTypeInfoResolver(new JsonConverterTypeInfoResolver().AddNullable<RocketId>().Add<Trajectory>());
```
 ## Enums [Section titled “Enums”](#enums) Rocket.Surgery.LaunchPad.Primitives ships a generator that registers a camel case `JsonStringEnumConverter<TEnum>` for every enum a JSON context of the project declares or reaches (through properties, collections and base types), and `SystemTextJsonJoint` adds those converters to the options. Generic converters need no dynamic code, so enums are camel case strings in a native AOT application too. An enum no JSON context reaches has no converter, and where reflection is available it is written as a number. An enum with a `[JsonConverter]` of its own keeps it. ## The API generators [Section titled “The API generators”](#the-api-generators) The generated Minimal API endpoints read and write through the HTTP JSON options. Generators can’t see each other’s output, so they can’t declare a context for you; in a project that sets `PublishAot`, `IsAotCompatible`, `PublishTrimmed` or `IsTrimmable`, **LPAD1030** names each body and response type that no context in the project or its references declares. Set `LaunchPadApiRequireJsonContext` to `true` or `false` to turn the check on or off for any project. See [API generators](../api-generators/#native-aot).

# Writing a Joint

> Add wiring of your own to an application or a library as a Joint that Dovetail applies with LaunchPad's.

Wiring of your own, in an application or in a library it references, is a [Joint](../../concepts/joints/) like LaunchPad’s. Dovetail finds it at build time and `ConfigureDovetail()` applies it with the rest. ## A service Joint [Section titled “A service Joint”](#a-service-joint) 
```csharp
using Joinery.Dovetail;
using Joinery.Dovetail.Attributes;
using Joinery.Dovetail.Joints;
using Microsoft.Extensions.DependencyInjection;


namespace MyCompany.Orders;


[DovetailExport]
public sealed class OrdersJoint : IServiceJoint
{
    public void Register(IDovetailContext context, IServiceCollection services) =>
        services.AddSingleton<IOrderRepository, OrderRepository>();
}
```
 * In an **application**, the Joint is applied by the application’s own `ConfigureDovetail()`. * In a **library**, `[DovetailExport]` exports it, and every application that references the library applies it. The library needs `Joinery.Dovetail` (or the [LaunchPad SDK](../../concepts/launchpad-sdk/), which adds it when the library references a technology LaunchPad supports). ## Options from the context [Section titled “Options from the context”](#options-from-the-context) A Joint can read settings from the `IDovetailContext`, which the application can fill before the Joints run. LaunchPad’s own Joints do this for their options; `TimeJoint` reads `NodaTimeOptions`: 
```csharp
public sealed class OrdersJoint : IServiceJoint, ISetupJoint
{
    // runs before any IServiceJoint, so the default is there for every Joint that asks
    void ISetupJoint.Register(IDovetailContext context) => _ = context.GetOrAdd(() => new OrdersOptions());


    public void Register(IDovetailContext context, IServiceCollection services) =>
        services.AddSingleton(context.Require<OrdersOptions>());
}
```
 ## Ordering and categories [Section titled “Ordering and categories”](#ordering-and-categories) Dovetail orders the Joints it applies. A Joint can declare what it must run after, and a `[DovetailCategory]`; one without a category is in the `Application` category. Dovetail’s documentation covers the interfaces, ordering, categories and injecting dependencies: [Defining Joints](https://rocketsurgeonsguild.github.io/Dovetail/concepts/defining-joints/). ## Testing a Joint [Section titled “Testing a Joint”](#testing-a-joint) LaunchPad’s own tests check a Joint through Dovetail’s generated exports: that it is exported, in the right category, and registers what it should. See [Unit tests](https://rocketsurgeonsguild.github.io/Dovetail/concepts/unit-tests/) in Dovetail’s documentation.
