# AGENTS.md

Guidance for AI coding agents (Claude Code, GitHub Copilot and others) working in this repository. Read the code and the tickets for the current state; this file records only what is stable enough to write down.

## What this repository is

LaunchPad is a set of `Rocket.Surgery.LaunchPad.*` libraries for building .NET console and web applications, published by the Rocket Surgeons Guild.

It was rebuilt for 2.0 on two building blocks, under the epic [RocketSurgeonsGuild/LaunchPad#3045](https://github.com/RocketSurgeonsGuild/LaunchPad/issues/3045):

- **Specular** provides AOT-safe assembly scanning.
- **Dovetail** provides build-time composition. A **Joint** is a unit of application wiring that Dovetail resolves and applies at build time; it replaces what LaunchPad used to call a convention.

The conversion is done: no project references `Rocket.Surgery.Conventions` or the old `Rocket.Surgery.Hosting` and `Rocket.Surgery.Extensions` packages any more, and on CI the whole solution builds and its tests pass ([#3056](https://github.com/RocketSurgeonsGuild/LaunchPad/issues/3056)). The migration plan, [`plans/dovetail-migration.md`](plans/dovetail-migration.md), is done and archived: do not update it. The ADRs in `docs/adr/` and the docs site describe what shipped, and what is left before the 2.0 release is tracked by the epic's sub-issues. The build pipeline in `build/` is on Dovetail too: `Rocket.Surgery.ModularPipelines.Extensions` ships its setup as joints, which `build/Build.cs` applies with `ConfigureDovetail()`. It is tooling outside the solution and takes its versions from `Directory.Packages.props` like everything else; it references `Joinery.Dovetail.ModularPipelines` and `Specular` directly because their generators write `ConfigureDovetail()` and the module scan into it. Its run history and duration estimates live in `.modularpipelines/` (gitignored), which CI restores from main.

- LaunchPad 2.0 targets **.NET 11 and later** ([#3239](https://github.com/RocketSurgeonsGuild/LaunchPad/issues/3239)). The target frameworks are declared once, as `LaunchPadTargetFrameworks` in `Directory.Build.props` (`net11.0`); every project in `src/`, `sample/` and `test/` reads it (`$(LaunchPadBrowserTargetFrameworks)` for WebAssembly, `$(LaunchPadLatestTargetFramework)` or `$(LaunchPadOldestTargetFramework)` for the few that build for one framework), and no project file names a framework itself, except the generators, analyzers, MSBuild task and SDK packages, which stay on `netstandard2.0`. The LaunchPad SDK stops a project on an older .NET with `LPADSDK0001`. A condition on a framework compares versions (`IsTargetFrameworkCompatible`, `NET12_0_OR_GREATER`), never equality. [`CONTRIBUTING.md`](CONTRIBUTING.md) lists everything that changes when a framework is added.
- Use the vocabulary in [`GLOSSARY.md`](GLOSSARY.md) (Joint, host model, integration package, direct reference, template, LaunchPad SDK) in code and docs you touch, and avoid the terms it marks as avoided.
- The reasons behind LaunchPad's main decisions are in [`docs/adr/`](docs/adr), among them that Joints replace conventions and that each integration is its own package.
- Package IDs and namespaces stay `Rocket.Surgery.LaunchPad.*`.
- Add, move or remove a package only under the ticket that owns it; the [readme](Readme.md) lists the packages there are.
- `LaunchPad.Hosting` ships its Joints as **templates** (`src/Hosting/build/*.cs.template`), not as compiled code, so the package depends on none of what they use. `src/Hosting/build/Rocket.Surgery.LaunchPad.Hosting.targets` declares them with Dovetail's `DovetailTemplate` item: a template is written into a project only if it has a direct reference to Hosting, declares one of the template's host models and references the assemblies it compiles against. NuGet imports those targets for a package reference; the root `Directory.Build.targets` imports them for the project references the samples and tests use. The header of the targets file says how to add a template, and `test/Hosting.Tests` packs the package and builds throwaway applications to prove each gate.
- `LaunchPad.Foundation` ships one template the same way, for the validators of `[Mutable]` view models:
  - The template is `src/Foundation/build/LaunchPadMutableValidatorsJoint.cs.template`.
  - `Rocket.Surgery.LaunchPad.Foundation.Templates.targets` declares it, and the root `Directory.Build.targets` imports those targets.
  - Its joint calls `AddLaunchPadMutableValidators()`, which the `[Mutable]` generator writes.
  - A project gets it when it references Foundation, ZeroAlloc.Validation and `Microsoft.Extensions.DependencyInjection.Abstractions`, and runs LaunchPad's analyzer.
- LaunchPad never serializes JSON through reflection ([ADR 0007](docs/adr/0007-no-json-reflection.md)). It takes ASP.NET Core's reflection resolver out of the HTTP JSON options of a JIT application too (`SystemJsonTextJoint`; `LaunchPadAspNetCoreJsonReflection=true` keeps it), and LPAD1030 reports every Minimal API body or response type no JSON context declares, in every project. `Rocket.Surgery.LaunchPad.Foundation` ships generators (in LaunchPad's one analyzer assembly, `src/Analyzers`) that write each library's **JSON context manifest** and the camel case enum converters, and an MSBuild task (`src/Foundation.Tasks`, declared in `src/Foundation/build/Rocket.Surgery.LaunchPad.Foundation.JsonContext.targets`) that writes an executable's JSON context from the manifests of its references. The root `Directory.Build.targets` imports those targets and has every project that writes a context build the task first; `src/Shared/MediatorLibraries.cs` is the mediator table the manifest and the API generators share.
- `LaunchPad.Primitives` is the optional **domain primitives** package, a port of [dotnet-domain-primitives](https://github.com/ericksonlopezf/dotnet-domain-primitives) (MIT, credited in `THIRD-PARTY-NOTICES.md`) ([ADR-0008](docs/adr/0008-primitives-is-an-independent-strong-types-package.md), [ADR-0011](docs/adr/0011-primitives-is-a-port-of-dotnet-domain-primitives.md)). It depends on no other LaunchPad package; an application opts in by referencing it, and the SDK never adds it.
  - An application declares its own domain primitives, `readonly partial record struct` or `sealed partial record` (a smart enum is a C# 15 `closed partial class` or a `readonly partial record struct`, never a `sealed partial record`: a closed class makes each member with `new` of its own nested class, named after the member with an underscore (`Pending = new Pending_(...)`), which the generator writes, its value first and then its data; a record struct makes each member with `new(value, ...)`, its value first and then its data, and gets `Match`, `Map`, `Switch` and `IsDefault` but no member classes), with exactly one primitive attribute: `[StringPrimitive]`, `[NumericPrimitive<T>]`, `[DatePrimitive]`, `[StrongId<T>]`, `[SmartEnum<T>]`, `[ValueObject]` or a primitive kind (`[Email]`, `[CurrencyCode]`, `[Money]`, ...), plus rules (`[MaxLength]`, `[Regex]`, `[Trim]`, ...). Primitives ships no ready-made types.
  - `src/Primitives` holds only what the generated code implements and uses. In `Rocket.Surgery.LaunchPad.Primitives`: `IDomainPrimitive<TSelf, TValue>` (one value), `IStrongId<TSelf, TValue>`, `IValueObject<TSelf>` (a value object; both extend `IDomainPrimitive<TSelf>`), `INormalizer<T>`, `ICustomValidator<T>`, `PrimitiveError`, `DomainPrimitiveValidationException` and the collection helpers. In namespaces of their own: `.Advanced` (`PrimitiveBuilder`, and `PrimitivePatterns`, the `[GeneratedRegex]` patterns of the primitive kinds, which the generated code matches against), `.Diagnostics` (`DomainPrimitivesInstrumentation`, the `Meter` and `ActivitySource` named `Rocket.Surgery.LaunchPad.Primitives`), `.Descriptions` (what the templates read about each domain primitive) and `.Registries` (`Iso3166Countries`, `Iso4217Currencies`).
  - `src/Primitives.Analyzers` (its own package, an exception to ADR-0004) holds every generator, analyzer (LPAD2001 and up; LPAD2101 and up for the generator) and code fix, except LPAD2024, which LaunchPad's own analyzer (`src/Analyzers/Primitives`) reports in an application that uses domain primitives through a library without referencing Primitives, as Primitives' analyzers don't run there. The attributes are not compiled into any assembly: the generator writes `Sources/PrimitiveAttributes.cs` into every project that references Primitives, `internal`, `[Conditional("CodeGeneration")]` and `[Embedded]`, as a C# 15 closed hierarchy (`PrimitiveAttribute` for the kinds, `PrimitiveRuleAttribute` for the rules). A domain primitive in a referenced assembly is found by `IDomainPrimitive<TSelf, TValue>` (a value object by `IValueObject<TSelf>`), never by its attributes. The NodaTime members of `DatePrimitiveKind` are behind `#if LAUNCHPAD_PRIMITIVES_NODATIME`, which the package's targets define when the project references NodaTime.
  - Its settings are MSBuild properties (`LaunchPadPrimitivesTrim`, `...NotEmpty`, `...MaxLength`, `...ExceptionType`, `...OpenApiRepresentation`, `...GraphQLRepresentation`) in `src/Primitives/build/Rocket.Surgery.LaunchPad.Primitives.targets`.
  - It ships its OpenAPI, HotChocolate, EF Core and OpenTelemetry Joints as templates the same way as Hosting (`src/Primitives/build/*.cs.template`, declared in `Rocket.Surgery.LaunchPad.Primitives.Templates.targets`, which the root `Directory.Build.targets` imports too), reading the `LaunchPadPrimitives` registry its generator fills in. The EF Core value converters, the Dapper type handlers and `AddLaunchPadPrimitivesInstrumentation()` are written by the registry generator (`src/Primitives.Analyzers/Registry`) when the application references those libraries; `ConfigureDomainPrimitives()` is in the EF Core template. `test/Sdk.Tests` (`SdkPrimitivesTests`) proves them end to end.
- `src/Sdks/LaunchPad` is the **LaunchPad SDK** (`Rocket.Surgery.LaunchPad.Sdk`), an MSBuild SDK an application applies with an `<Sdk>` element in each project (`#:sdk` in a file-based app) or once in its `Directory.Build.props`. It chains `Joinery.Dovetail.Sdk` (the version `Directory.Packages.props` pins for it) and adds LaunchPad packages from what Dovetail's host detection finds and from the project's direct `PackageReference`s; `LaunchPadEnable<Tech>=false` opts out. Every LaunchPad SDK also chains the **Chirograph** SDK (OpenAPI clients from `OpenApiClient` items) through `src/Sdks/LaunchPad/Sdk/Rocket.Surgery.LaunchPad.Chirograph.targets`, after the project body, unless the project applies Chirograph itself or sets `LaunchPadEnableChirograph=false`; the repository's own test projects apply `<Sdk Name="Chirograph" />` directly, at the version `global.json` pins, which must equal the `Chirograph` `PackageVersion`. The versions are written into `Sdk/Packages.props` when the SDK is packed. `src/Sdks/Console` is the **console SDK** (`Rocket.Surgery.LaunchPad.Sdk.Console`): the same SDK for ConsoleAppFramework applications, chaining `Joinery.Dovetail.Sdk.Console`. `src/Sdks/{Web,Worker,Razor,BlazorWebAssembly,WebAssembly,WindowsDesktop}` are the **mirrors** (`Rocket.Surgery.LaunchPad.Sdk.Web`, ...): each is the Microsoft SDK of the same name with LaunchPad, chains Dovetail's mirror (`Joinery.Dovetail.Sdk.Web`, ...) and then applies `src/Sdks/Mirror/Rocket.Surgery.LaunchPad.Mirror.props`, which skips LaunchPad when a `Directory.Build.props` already applied it. Every SDK but `Rocket.Surgery.LaunchPad.Sdk` packs the shared files of `src/Sdks/LaunchPad/Sdk` beside its own `Sdk.props`/`Sdk.targets`; `src/Sdks/Directory.Build.props`/`.targets` hold the package settings and generate each `Sdk/Packages.props` from `LaunchPadChainedSdk`. `test/Sdk.Tests` packs it and builds throwaway applications against it, and `sample/Sample.Sdk` consumes it from packed packages (`dotnet msbuild build/pack.proj` there first). Like an application outside the repository, that sample and the throwaway projects of the tests stand outside central package management and name their own versions.
- An operation that can fail responds with a **union response** instead of throwing ([`docs/design/union-types.md`](docs/design/union-types.md), [ADR-0005](docs/adr/0005-portable-unions-shaped-like-csharp-unions.md), [ADR-0010](docs/adr/0010-net11-only-and-native-unions.md), [ADR-0006](docs/adr/0006-union-responses-over-every-transport.md)); the generated servers answer each error case in their transport's error shape. Unions are native C# 15 unions (`public union Result(RocketModel, NotFound);`), or hand-written custom unions; LaunchPad has no union generator and no polyfill ([ADR-0010](docs/adr/0010-net11-only-and-native-unions.md)). The standard error cases (`Problem`, `NotFound` and the rest) are in Foundation. Generators detect a union by name (`UnionAttribute` or `IUnion`), take its cases from its public one-parameter constructors (implicitly declared ones included) and read it through `Value`.
- An operation is authorized by the **policies** on its request ([`docs/design/authorization.md`](docs/design/authorization.md), [ADR-0011](docs/adr/0011-request-policies-publish-scopes.md)): ZeroAlloc.Authorization's `[RequirePolicy]` and `[RequireAnyPolicy]`, on `[Policy]` classes that declare their scopes with LaunchPad's `[RequiresScopes]`. `src/ZeroAlloc.Authorization` (`Rocket.Surgery.LaunchPad.ZeroAlloc.Authorization`, types in `Rocket.Surgery.LaunchPad.Authorization`) holds the pipeline behavior, which answers the `Unauthorized` or `Forbidden` case of the response union; LaunchPad does not use ZeroAlloc.Mediator.Authorization. `src/Analyzers/Authorization` writes each request's authorization plan, reports LPAD1050 to LPAD1054, and is where the API generators read policies (`PolicyReader`). `ZeroAlloc.AspNetCore` has the **edge**: an operation whose request has policies carries the ASP.NET Core policy `launchpad:{request type}`, which runs the plan before the request is bound and records the outcomes the pipeline reuses, and the scopes go into the OpenAPI document. `ZeroAlloc.HotChocolate` declares `@requiresScopes` and `@authenticated`. Every `Sample.Core` request has a policy: `Sample.AppHost` runs Keycloak (`sample/Sample.AppHost/Realms/launchpad-realm.json`), and the web fixtures of `test/TestSupport` trust test tokens (`TestTokens`) and send the default caller's with any request that has no `Authorization` header.
- Every test project runs on TUnit with Microsoft.Testing.Platform, as moved by tickets [#3050](https://github.com/RocketSurgeonsGuild/LaunchPad/issues/3050) and [#3051](https://github.com/RocketSurgeonsGuild/LaunchPad/issues/3051); `test/Directory.Build.targets` adds the TUnit, Verify.TUnit, TUnit.Mocks and TUnit.Assertions.Should packages to each of them, and there is no xunit, FakeItEasy or Shouldly anywhere. Tests assert with the Should syntax (`await x.Should().BeEqualTo(y)`), falling back to `Assert.That` only where it has no equivalent, and mock with TUnit.Mocks. A test that resolves services from a populated service collection derives from `ContainerTest<TestRecord>` (`test/Shared/ContainerTest.cs`, linked into the projects that use it). The same file gives every test project `Joinery.Dovetail` and Specular, so a test gets the joints and the Specular scan results of the projects it references. Shared test code (the web app fixtures and fake time) lives in the non-packable `test/TestSupport` project. A test creates scopes directly with `CreateScope()` / `CreateAsyncScope()`.

## Repository layout

| Path                 | Contents                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `src/`               | One folder per package (`Foundation`, `Hosting`, `AspNetCore`, `Grpc`, and so on)                                                    |
| `test/`              | Test projects, including `Sample.*.Tests` for the samples                                                                            |
| `sample/`            | `Sample.*` applications                                                                                                              |
| `build/`             | The build pipeline: `Build.cs` is a file-based app that runs ModularPipelines (`Samples.cs` has the AOT publish of selected samples) |
| `docs/`              | The Astro/Starlight documentation site, plus the ADRs in `docs/adr/`                                                                 |
| `.config/`           | `mise.toml` (tools and tasks) and `hk.pkl` (lint and format steps)                                                                   |
| `.github/workflows/` | CI: `build.yml` runs `mise run build`, `lint.yml` runs `hk` through autofix.ci                                                       |

The solution is `LaunchPad.slnx`, and it builds cleanly on CI (linux x64). On macOS arm64 without Rosetta the gRPC sample does not build, because `Grpc.Tools` ships only an x64 `protoc` for macOS.

## Build, test and format

- Tools come from mise. `mise install` installs what `.config/mise.toml` pins: the .NET SDK that `global.json` asks for, node, hk, biome, oxfmt and so on. `global.json` also selects the Microsoft.Testing.Platform test runner.
- mise sets `DOTNET_ROLL_FORWARD=Major`. StrawberryShake's code generator targets .NET 9, and this lets it run on the .NET 11 runtime, the only one mise installs.
- Build with `mise run build`, which runs `dotnet run build/Build.cs`. The docs site has its own tasks: `mise run docs`, `mise run docs:build` and `mise run docs:preview`.
- Package versions are central: add them to `Directory.Packages.props` (samples have their own `sample/Directory.Packages.props`) and never put a `Version` in a `.csproj`.
- Formatting and linting run through hk (`.config/hk.pkl`): `hk check` verifies and `hk fix` applies fixes. Biome formats JavaScript, TypeScript and JSON, oxfmt formats YAML, Markdown, CSS and HTML (style and ignores in `.oxfmtrc.json`), tombi formats TOML and `dotnet format` handles C#. Generated agent files are excluded.
- `.editorconfig` holds the editor settings. The recommended editor extension for formatting is Biome (`biomejs.biome`).

## Agent tooling

The agent packages and skills are managed the same way as in [Dovetail](https://github.com/RocketSurgeonsGuild/Dovetail):

- `apm.yml` lists the agent packages and `Skillfile` declares the install targets (Claude Code and Copilot, locally).
- `.config/mise.toml` pins the `apm` and `skillfile` tools.
- Install with `mise install`, then `mise exec -- apm install` and `mise exec -- skillfile install`.
- `apm.lock.yaml` and the files apm deploys (skills and agents under `.agents/`, `.claude/` and `.github/`) are committed. Regenerate them with the commands above instead of editing them by hand.
- `apm_modules/` and the machine-local files `apm install` writes (listed in `.gitignore`) are not committed.
